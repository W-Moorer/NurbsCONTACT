# CPU 减速器的网格计时复核与 CAD 承载区分块积分

## 网格计时

同一台 Ryzen 9 5900X 上使用原两级减速器、0.1 ms 步长、共享罚刚度和预测姿态 HHT。原两次仿真与慢批可执行文件的复测都跑满 5 s。三份响应文件的 SHA-256 一致，各执行 420,692,832 次三角片检验、151,547 次力评估以及 7,530 次面对 BVH 构建。

| 网格对照 | 进程墙钟时间 | 积分 | 接触检测 |
| --- | ---: | ---: | ---: |
| 原快批 | 289.32 s | 279.27 s | 273.13 s |
| 原慢批 | 712.13 s | 684.37 s | 666.36 s |
| 慢批的同一二进制单独复测 | 284.81 s | 273.36 s | 267.31 s |

422.81 s 的差额中有 393.23 s 出现在网格接触检测，占 93.0%。按每 0.5 s 仿真时间拆分，慢批的十个窗口分别用时为快批的 2.23 至 2.60 倍。旧进程的两个 Release 二进制另按 A–B–B–A 顺序运行同一段 800 步轨迹，四次检测用时 13.17、13.06、13.00、13.87 s，响应文件和几何工作量相同。短例只用于区分版本效应，表中三项均为完整闭环。

慢批程序回到约 285 s，说明旧慢批的主机执行条件影响了计时。两次旧运行没有逐时段的进程 CPU 时间和硬件计数，温度、时钟限制和后台调度各自造成了多少秒，现有资料不能分解。本次复测每三秒记录 Windows 进程用户/内核时间、周期计数和系统性能计数器。慢批程序复测的累计用户时间为 377.66 s，内核时间为 102.81 s，这两项跨线程累加。[历史窗口、交叉对照和监测记录](mesh-timing.json)

## 通用分块积分

每个面按原 UV 积分规则划分小块，预存每块有向面积、面积一阶矩、标量面积和加权位置。完全承载的块一次累加有向面积和力矩。部分承载的块按实际命中点计算。块内各法向线段共用原实体的候选面表，每条射线仍可检查更早的遮挡面。承载区合并后沿用同一接触深度和罚力定律。

设积分点的本体位置为 $p_i$，有向面积为 $a_i$。预处理保存 $A_B=\sum_i a_i$ 和 $M_B=\sum_i p_i\times a_i$。零件姿态为 $(R,t)$ 时，整个承载块对参考点 $o$ 的面积矩贡献为 $R M_B+(t-o)\times R A_B$。两侧按各自外法向取符号，在连通接触区内汇总，再乘同一力定律给出的载荷尺度。

体积和质心还依赖材料法向柱的厚度。对矩形裁剪的多项式曲面，若控制网能验证一个方向的整条母线平移后截面保持一致、所有可能相交的面均允许这次平移、射线位于裁剪边界内，且首尾柱的深度和命中面一致，便能用预存量一次完成同厚度块的体积和质心积分。一般曲面保留各柱的深度计算。算法没有用齿号、啮合相位或预存轨迹。

## 整块积分的五秒结果

| 方法 | 进程墙钟 | 普通步均值 | 输出轴力矩与 RecurDyn 的 RMS 差 |
| --- | ---: | ---: | ---: |
| 逐柱 CAD，串行局部求交（历史） | 963.02 s | 见[原始批次](../columns/serial-clipped.json) | 42.09 N·m |
| 逐柱 CAD，并行局部求交（历史） | 1,256.98 s | 21.41 ms | 42.09 N·m |
| 整块积分 CAD（ours） | 1,212.65 s | 20.34 ms | 42.09 N·m |
| 同一程序的 Gmsh 三角网格 OBB | 367.03 s | 7.07 ms | 29.14 N·m |

表中每行均完成 50,000 个主步。最后两行按 CAD、网格的顺序独立运行，均含启动和输出。该批 CAD 耗时是网格的 3.30 倍，963.02 s 那批为 963.02 / 289.32 = 3.33 倍。复测历史网格与本批网格的 Windows 全系统处理器性能计数中位数分别为 30.49% 和 24.72%，本批 CAD 为 19.45%。这个指标覆盖所有处理器，无法据此将一种方法的耗时换算到另一批次。[网格分段计时图](mesh-timing.png)

全程有 462,365 个完全承载块一次累加合力方向与力矩，1,482,576 个部分承载块按实际覆盖点计算。通过同厚度验证共省下 40 次逐柱深度查询。面积积分在两个接触对上累计耗时 601.61 s，接触区分组 263.71 s，寻找接触面 241.48 s，粗筛 109.62 s。两级任务可并行，分项计时有重叠。17 个局部求交主步共耗 122.00 s，整实体求交为零。保持本次启动、写盘和 17 步的开销，300 s 预算允许其余每步用 2.08 ms，实测为 20.34 ms。

每级回放同样的 800 个姿态，包含一级 163 次、二级 142 次面对分组的变化。整块积分与逐柱积分的分组逐帧一致。同姿态复测中，一级的 7,363 个非空块全部承载，二级有 652 个完全承载块和 24,730 个部分承载块。二级在这 800 帧省下的逐柱深度查询为零。两次计时的一级积分均值分别从 2.52、2.17 ms 降到 2.22、2.08 ms，二级分别从 12.22、9.26 ms 降到 10.09、8.66 ms。两次复测均显示局部收益，批次间的差异也很明显。[第一轮同姿态计时](fixed-first-pass.json)

另做了一组相邻姿态复用候选块和 Bézier 子块的对照。复用前后，一级积分均值从 2.01 降为 1.91 ms，二级从 9.02 增为 9.54 ms，两级均值之和增加 3.7%。两级分别复用了 2,002 和 3,984 次候选表，访问 Bézier 块和调用原生内核的次数均未减少。核对同厚度条件时，一级有 6,150 个源块满足直线平移条件，其中仅 2 个能同时确认所有可能相交的对侧曲面也满足条件。二级有 9,615 个块的首柱合格，满足平行源柱条件的为零。这解释了该减速器上共用柱深机会少的原因。本次交付使用上表跑完五秒的整块积分实现。候选表试验只计同姿态回放，保留[测量数据](window-trial.json)和[可复算的补丁](window-trial.patch)。在该版本的独立工作目录应用补丁，重新编译两个探测程序，再用下方的 `paired` 命令比对即可。

## 复算

在仓库根目录准备[同一场景与运行库](../README.md)，设置 `OMP_NUM_THREADS=2`，将 `NC_CAD_CACHE_DIR` 指向相同的零件表。计时程序在 Windows 上运行。每种方法单独启动，单次时限 1,800 s。

[CAD 运行记录](cad-bezier-run.json)和[网格运行记录](mesh-obb-run.json)包含场景、可执行文件、原始轨迹的 SHA-256。撤回候选表试验后，从交付源代码重新编译的 `nc_contact.exe` 与五秒计时所用程序的 PE `.text` 节 SHA-256 均为 `d74818922ff89fbdfbbceb9f4ca867875fd94891aed3264cbdb824c343d1d831`。

```powershell
python benchmarks/aes/cpu_process_timing.py crossed $scene build/timing-ab $previousExe $slowBatchExe
python benchmarks/aes/cpu_process_timing.py mesh-obb $scene build/repeat-original $slowBatchExe
python benchmarks/aes/cpu_block_report.py mesh $scene $fastRun $slowRun build/repeat-original build/timing-ab/crossed.json
foreach ($method in @("cad-bezier","mesh-obb")) {
    python benchmarks/aes/cpu_process_timing.py $method $scene "build/block-cycle/$method" $currentExe
}
python benchmarks/aes/cpu_block_report.py dynamics $scene build/block-cycle --serial-run $serialCadRun
python benchmarks/aes/cpu_pressure_columns.py paired $scene $previousProbes --probes $currentProbes --out results/aes/cpu-bezier/blocks
```
